# Security Considerations

**Status: M4 complete; current through M6.** The trust-boundary threats
(spoofing, header precedence, provider hardening), the MaxMind file-read
threat, and the remote-provider threats (SSRF, API-key disclosure, DoS via
latency) below are implemented and tested. M5 (WP-CLI, Site Health
`debug_information`, Privacy Policy Guide integration) introduces no new
threat class: WP-CLI access already implies server/deploy-level trust
equivalent to `wp eval`, and both the `diagnostics` command and the
`debug_information` section reuse the same already-masked
`DiagnosticsService::report()` the admin Diagnostics tab does — no new
code path can expose a credential or a complete IP address. M6 (managed
GeoLite2 database downloads) introduces genuinely new threat surface —
credential-bearing outbound requests, untrusted archive extraction, and
filesystem writes to an admin-controlled managed directory — each
addressed below.

## Threat model

| Threat | Mitigation |
|---|---|
| **Header spoofing → forged country** | Fail-closed trust model (§ see `docs/TRUSTED_PROXIES.md`): with no trusted proxies configured, every forwarding header is ignored; right-to-left `X-Forwarded-For` walk; the immediate peer must be verified before any header is read at all. |
| **Forged country used for authorisation** | Documented prohibition (the plugin's public API contract): geo is evidence, never authentication. Never use the resolved country as the sole basis for access control, pricing eligibility, or compliance exemptions. |
| **Arbitrary file read via a MaxMind database path** | Mitigated as shipped (M3). The settings field is constrained under `WP_CONTENT_DIR`: syntactic shape only in `Settings::sanitize()` (no filesystem I/O in that purity boundary), then `realpath()` + `is_file()` + `is_readable()` + containment checked in `AdminScreen::handle_save_settings()` at save time, and revalidated again in `Plugin::resolved_maxmind_db_path()` at every graph construction (never trusting that a stored value necessarily came from the admin form). The WooCommerce auto-detected candidate is held to the identical containment check, since it is likewise option-derived. A `wp-config.php` constant (`UNIVERSAL_GEO_MAXMIND_DB`) and the `universal_geo_maxmind_db_path` filter are the only two escape hatches allowed to point outside `WP_CONTENT_DIR` — both are code-level surfaces, unreachable from an admin-panel attacker who can only write options. The provider's own use-time check (`is_readable()`) never echoes file contents back to any consumer. |
| **Hostile third-party providers** (including filter-registered ones via `universal_geo_providers`) | Every candidate is re-validated by `GeoValidator` before use, regardless of source; confidence is assigned only from `ContextResolver`'s own table, keyed by provider id — a provider (or a filter) can never mint its own confidence or a `1.0` score; every `resolve()` call is wrapped in `try/catch(Throwable)`, so a throwing provider degrades to a skip, never a fatal page view; the `universal_geo_context` filter's return value is itself re-validated (non-`VisitorContext`, or a structurally-valid-but-not-real country code, is discarded and the original context kept). |
| **WooCommerce's own public geolocation filters** (`woocommerce_geolocate_ip`, `woocommerce_get_geolocation`) | `WooCommerceProvider` calls `WC_Geolocation::geolocate_ip($ip, false, false)` with an explicit IP and both fallbacks disabled — no outbound HTTP, no left-to-right `X-Forwarded-For` re-read. A `private static` re-entrancy guard makes a nested re-entry (from a site wiring this plugin back into those same filters) return `null` immediately rather than recursing. |
| **SSRF via remote providers** | Mitigated as shipped (M4). `ReferenceRemoteProvider` builds a hardcoded request URL (`https://geolite.info/geoip/v2.1/country/{ip}`) — no admin-supplied base URL exists anywhere. `WordPressHttpTransport` is the only production file permitted to call `wp_safe_remote_get()` (`PrivacyGuardTest` rule 8, per-file *and* per-function — even that one file may not use `wp_remote_get`/`wp_remote_post`/`wp_remote_request`/`curl_init`, rule 6), and always disables redirects (`redirection => 0`), caps the response body (`limit_response_size => 16384`), and bounds the timeout to 1–5 seconds (the admin-configurable `remote_timeout` setting, default 2s, clamped by `Settings::sanitize()`; `WordPressHttpTransport` re-clamps to the identical range defensively). No retries exist. |
| **API-key disclosure** | Mitigated as shipped (M4), extended (M6). `DiagnosticsService`'s remote and managed-database sections and their Site Health tests report only a `credentials_present` boolean and a `credential_source` enum (`constants`/`settings`/`none`) — the account id and license key values themselves are never rendered, logged, or included in any hook payload. As of M6, the remote provider and managed downloads share one canonical credential pair (`maxmind_account_id`/`maxmind_license_key`), resolved exactly once, in `Plugin::resolved_maxmind_credentials()`: the canonical `UNIVERSAL_GEO_MAXMIND_ACCOUNT_ID`/`UNIVERSAL_GEO_MAXMIND_LICENSE_KEY` wp-config.php constants take precedence, falling back to the deprecated legacy `UNIVERSAL_GEO_REMOTE_ACCOUNT_ID`/`UNIVERSAL_GEO_REMOTE_LICENSE_KEY` pair, falling back to the settings pair (itself migrated non-destructively from the legacy settings fields the first time both canonical fields are blank) — a constant pair always wins over settings as a pair, never one constant combined with one setting. The settings-tab credential fields are `type="password"`, never round-trip the stored value, and a blank submission preserves the existing value rather than erasing it (an explicit "Clear stored credentials" checkbox is the only way to blank them, now parameterized by `AdminScreen::submitted_credential()` so both the remote and managed-database UI sections share the identical never-round-trip behavior). No WP-CLI command accepts a credential flag (M6's `Cli\DatabaseCommand` included) — shell history and process-list exposure are avoided by reading credentials only from the persisted/constant sources. |
| **Credential leakage to a download redirect target (M6)** | The GeoLite2 download endpoint (`download.maxmind.com`) 302-redirects to a presigned Cloudflare R2 URL. `DatabaseManager::download_now()` never lets `wp_safe_remote_get()` auto-follow that redirect. It performs two explicit, independently-timed requests: `WordPressHttpTransport::get_redirect_location()` (with `redirection => 0` and the Basic Auth header) only detects a 3xx and reads `Location` — it never fetches the redirect target. `RedirectValidator::validate()` (stateless, pure) then rejects anything not `https`, anything carrying userinfo, and any host outside a small documented allowlist (`r2.cloudflarestorage.com`). Only a validated target is fetched, via `WordPressHttpTransport::download()`, with an **explicitly empty headers array** — not an omission, a deliberate absence — and `redirection => 0` again, so if the validated target itself answers with a further redirect, that is a terminal failure, never a third hop. A dedicated test (`DatabaseManagerTest`/the credential-isolation proof) asserts, via `FakeHttpTransport`'s per-call header recording, that the Authorization header is present on the first call and absent on the second — proving isolation, not just asserting the code looks right. |
| **Untrusted archive extraction (M6)** | The downloaded `.tar.gz` is treated as hostile input. `ArchiveExtractor` uses `PharData` but never calls `extractTo()` (which would honor archive-supplied paths, i.e. zip-slip); it iterates entries and copies bytes for the one entry matching the expected filename by exact basename only, to a destination path the code itself chose — path traversal via `../` or absolute paths in the archive is structurally impossible, not merely filtered. Extraction is byte-capped (`MAX_ARCHIVE_BYTES`, injectable in tests) against a decompression-bomb archive; an archive containing zero or multiple candidates matching the expected name is rejected (`ArchiveException::ambiguous_candidates()`) rather than guessed at. |
| **Partial download / install-time corruption (M6)** | A candidate database is validated twice before it can affect production resolution: once before install (structural: non-empty, plausible size, `Reader`-openable, `databaseType` contains `Country`, plausible non-future `buildEpoch`, a lookup against a fixed test IP completes without throwing) and once again immediately after the atomic rename, re-opening the just-installed file fresh. The install itself is same-volume `rename()` (active→`.previous`, candidate→active) — atomic at the filesystem level, so a crash mid-install cannot leave a half-written file live. If post-install verification fails, `.previous` is restored if one exists; otherwise the site is left with no managed database rather than a corrupt one — `MaxMindProvider`'s own `is_readable()`/open-failure handling degrades that to a normal provider miss, never a fatal page view (invariant 5). |
| **Concurrent update races (M6)** | Admin-triggered, WP-Cron-triggered, and WP-CLI-triggered updates all funnel through `DatabaseManager`'s three action methods, each gated by `UpdateLock` — a single option-backed, token-based cooperative lock with a 600-second TTL for stale recovery. This is explicitly **approximate**, the same documented philosophy `CircuitBreaker` already uses for its own state — the real safety net against corruption is the atomic-rename install algorithm above, not lock perfection; a lock race can at worst cause a redundant download, never a corrupt install. |
| **Checksum verification (M6/M6J)** | GeoLite2 downloads are validated both structurally (see "Partial download" above) and cryptographically: `DatabaseManager::fetch_checksum()` fetches MaxMind's `.sha256` sidecar (`CHECKSUM_ENDPOINT`) via the identical redirect-safe two-hop flow the archive itself uses — confirmed, against a live MaxMind account during M6J acceptance, to redirect through the same `RedirectValidator`-allowlisted host, so no new credential-exposure surface is introduced. The reported digest is compared via `hash_equals()` against `hash_file('sha256', ...)` computed over the just-downloaded archive; a response that doesn't parse as `<64 hex chars><space(s)><filename>`, references an unexpected filename, or simply mismatches, aborts the update (`checksum_mismatch`/`checksum_unavailable`) with the previously installed database left untouched — this gate fails closed, exactly like the structural MMDB validation it sits alongside. |
| **Admin CSRF** | Every settings write (`handle_save_settings`, the two diagnostics affordances `handle_trust_peer`/`handle_enable_cf_preset`, and, as of M6, the four managed-database actions `handle_maxmind_database_download/validate/remove/restore`) requires `manage_options` **and** a verified nonce (`check_admin_referer()`); the Diagnostics tab is read-only and still capability-gated. The two destructive M6 actions (remove, restore) additionally require a JS confirmation step in the browser — a UX safeguard only, not a security boundary, since the server-side nonce+capability check is what actually enforces the action. |
| **Information disclosure via diagnostics / Site Health** | Every address anywhere in the diagnostics report or either Site Health test passes through `IpUtils::mask()` first — never a complete IP. The `universal_geo_provider_failed` action's live payload is the failing exception's class and message verbatim (unchanged since M2 — consumers were already warned it may contain arbitrary text), but the *persisted* copy `ProviderHealthStore` writes is scrubbed of IP-shaped tokens and truncated to a bounded length before it ever reaches `wp_options`, and the admin Diagnostics tab renders only that already-scrubbed copy. |
| **Cache poisoning** | The derived-context cache key includes a per-site salt (never persisted in plaintext form usable to reverse it without brute force) and a settings signature (`config_sig`) covering every resolution-affecting setting — a configuration change cannot serve a context computed under the old rules, and the settings-save handler bumps the invalidation epoch on every save. |
| **DoS via provider latency** | Local providers (`CloudflareHeaderProvider`, `WooCommerceProvider`, `MaxMindProvider`) perform no network I/O; `MaxMindProvider` additionally opens its `Reader` at most once per request (memoized, including a failed open, so a corrupt database costs one attempt, not one per lookup). The remote provider (M4) bounds its own timeout to 1–5 seconds (default 2s — the page-view latency bound, G10) and, more importantly, is gated by a dedicated `CircuitBreaker`: three consecutive failures open the circuit for 300 seconds, during which every request skips the outbound attempt entirely and falls straight through to the next provider — a slow or unreachable remote endpoint degrades to "no worse than local-only resolution," never to "every page view waits on it." No retries exist at any layer. |
| **Trusted-proxy misconfiguration** (the most likely way this plugin silently returns wrong data for every visitor) | Fail-closed default; the `universal_geo_trusted_proxy` Site Health test flags **critical** when forwarding headers are present, the peer is private, and no trusted proxies are configured; a first-run admin notice surfaces the same condition proactively; `docs/TRUSTED_PROXIES.md`'s recipe table covers every common topology. |
| **Chained Cloudflare mode is spoofable when the origin is directly reachable** | Documented, not silently mitigated: if a site's origin answers HTTPS directly (bypassing the CDN/proxy), an attacker who discovers that origin IP can forge `CF-*` headers through the trusted inner proxy. The chained-mode toggle is always an explicit admin assertion, never a default; the recipe in `docs/TRUSTED_PROXIES.md` recommends locking the edge to proxy-only ingress. |

## Provider hardening, stated as invariants

- A provider never receives write access to any plugin state; it returns a
  `GeoCandidate` (country + region facts only) or `null`, nothing else.
- No provider — built-in or filter-registered — can assign its own
  confidence. `ContextResolver`'s confidence table is keyed by provider id;
  an unrecognized id (a third-party provider registered via the
  `universal_geo_providers` filter) receives a fixed, capped, "unlisted"
  confidence rather than being trusted implicitly.
- A provider throwing any `Throwable` is caught at the resolver loop and
  treated exactly like a miss — the chain continues to the next provider.
  This is the single most important operational property of the resolver:
  no third-party provider bug can fatal a page view.
- `CloudflareHeaderProvider`'s availability is gated entirely on the trust
  verdict `ClientIpResolver` computes once per request — it never re-derives
  or duplicates that decision, so there is exactly one place in the codebase
  that decides whether a Cloudflare header may be trusted this request.

## Page caching

The plugin resolves per-request in PHP. If cached HTML is varied by
geography, every visitor sees the first visitor's country baked into the
cache. **The plugin does not solve this and does not claim to.** Three
strategies exist, and each belongs to the site operator or the consuming
plugin, not to Universal Geo Context itself: restrict geo-dependent output
to never-cached surfaces (admin-ajax, a logged-in-only area); vary the edge
cache key on the resolved country (an operator-level CDN configuration);
resolve client-side via a REST endpoint (sketched for a future release, not
shipped in v1).

## Zero front-end footprint

No cookies, no sessions, no JavaScript, no CSS, no output on the front end.
Resolution happens entirely server-side, on demand.

See `docs/PRIVACY.md` for the full persisted-data inventory and GDPR framing,
and `docs/TRUSTED_PROXIES.md` for the trust-boundary deployment recipes this
threat model depends on.
